# Multi-server desktop client

The Electron desktop client connects to multiple servers, presented as a "Discord-like" server rail. Each server is an independent identity island with its own origin, session cookie (ADR-0008), and library. The client stores an ordered list of **server profiles** (URL + display name) locally via `electron-store`; selecting a server loads that server's bundled PWA at its origin in an isolated session partition. Per-server client preferences (e.g. active theme) are keyed by profile. The PWA itself remains single-server; multi-server in the PWA is deferred to a later phase.

This does not contradict ADR-0004 (one server hosts one library). That decision is about a *server*; this one is about the *client* aggregating N servers. Each server still hosts exactly one library, and permissions/sessions remain per-user-per-server (ADR-0004, ADR-0008). The client simply holds several of them at once and switches between them.

This was chosen over the single-server thin launcher originally scoped in PLAN 2.3 because users run or join several servers and want one desktop app to move between them without relaunching against a different URL. It was chosen to live in the desktop client rather than the PWA because same-origin session cookies (ADR-0002, ADR-0008) make holding N servers in a single browser page awkward. Cross-origin auth, CORS, and cookie partitioning all fight it. The Electron shell sidesteps this by giving each server its own web-contents/session partition.

The cost is that the launcher grows from the ~200-line thin shell (ADR-0002) into a stateful multi-connection shell: per-server session partitions, a switcher UI, and profile storage. It still holds no data-access layer. Each connection is an isolated PWA view over its server's API, so no v1-style client data plumbing returns. PWA users remain single-server until a future phase revisits it; the upgrade path there is additive (a server picker plus per-server auth), not a rewrite of this decision.

> **Realized/updated by ADR-0014 (v2.2).** This ADR described per-server session partitions, but the code had not actually set them (the window did `loadURL(serverUrl)` with a shared session). ADR-0014 implements the intent: a persistent sidebar (not a Discord-style icon rail, and without v1's publish/import section) as fixed chrome, each server embedded in a `WebContentsView` under its own `persist:srv-<id>` partition, so every server stays logged in and switching is instant. See ADR-0014.
